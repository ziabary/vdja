# T4 identity and session contract (work in progress)

Identity is deployment-global. Membership is keyed by identity and tenant. Authentication verifies a human credential; the Session capability owns tenant-bound sessions and refresh-token families. Authority alone evaluates permissions. Anonymous requests use `actorKind=ANONYMOUS`, null actor/session IDs and the deployment's public tenant.

The production transition proposed for T4 is `credential proof → tenant selection → new tenant-bound session → short-lived access token`. A tenant switch creates a new session context. Access-token claims are identity ID, tenant ID, session ID and authorization version; the database remains canonical. Refresh tokens are high-entropy opaque credentials; only hashes and rotation history are persisted. A refresh consumes the current token atomically. Reuse revokes the family. Revocation and version changes must invalidate already-issued access tokens through a database check on every protected request.

Current target-path state: the pure Authority kernel passes 39 conformance cases. PostgreSQL migration `004` owns global identity, tenant membership, password credential, durable login guard, sessions and refresh history. Authentication resolves credentials and active memberships from PostgreSQL, verifies passwords centrally, and uses durable account/address guards. The optional Auth API provides login with explicit selection for multiple tenants, refresh, logout and a bearer-protected account/session view. Ed25519 access tokens have minimal claims, a five-minute maximum lifetime, issuer/audience and `kid` validation, and keys loaded from secret references. The protected-request verifier checks canonical session, identity, membership, tenant and authorization version in PostgreSQL. The Web gateway does not route `/api/auth/*`; the browser sends Auth requests directly to the configured HTTPS Auth hostname with credentialed CORS. A BrandProfile-based Svelte login page appears only when Auth is enabled, with its access token held in component memory. Authenticated Translator, Summarizer and FAQ requests use production Authority, tenant-scoped PostgreSQL facts, differentiated Admission limits, HUMAN Usage, semantic Audit and SIEM export. Unit, PostgreSQL/HTTP, and two-host HTTPS Chrome tests cover these target paths; Chrome uses a mocked backend while independent PostgreSQL/HTTP tests exercise the real API. MFA, password change/recovery, full session management, full persisted Authority coverage and a coordinated Auth-enabled customer release remain open.

The `session_core` schema owns session and refresh history. The `identity` schema owns global identity and tenant membership. `authentication` owns password credentials and login guard facts. `authority` owns permission vocabulary, roles, grants/denies, ACL and clearance facts. Privilege evaluation lives only in `packages/authority/src/index.ts`; it receives explicit time and normalized facts. The API uses the new Auth/Session tables and tenant-scoped Authority persistence for authenticated public tools. Generic persisted ACL, classification, clearance and recurring-grant behavior still lacks a complete production-path matrix.

The password implementation uses Node's standard scrypt with N=2^17, r=8, p=1 and a fresh 128-bit salt. Local screening rejects a ranked set of 3,000 common passwords at hash creation. The new password policy also rejects configured context words after NFKC normalization, Arabic/Persian kaf and yeh normalization, and Unicode lowercasing, and checks a local SHA-1 prefix corpus or HTTPS range provider. A missing local shard, malformed corpus, unavailable range provider, or timeout fails closed. Auth-enabled configuration requires an explicit breach provider and derives context terms from Brand and Deployment plus configured terms. This policy has unit evidence but no operational change/recovery path uses it yet; password ASVS findings remain open. A tiny test corpus is not a production breached-password corpus. Login guards lock account and address keys after bounded failures; the PostgreSQL integration test passed with real credentials and unknown-account lockout. Refresh tokens have 256 random bits and only SHA-256 hashes enter PostgreSQL. Session creation checks active human identity and membership. Refresh rotation locks token/session/membership/identity rows in one PostgreSQL transaction. Reuse of a consumed token revokes the family. Logout revokes the session by hashed refresh credential. Access-token validation rejects revoked or expired sessions, identity or membership suspension, version mismatch and tenant mismatch. Credential-change invalidation, tenant switch and selected/all-session revocation remain open. Existing login, refresh, replay, logout, Authority denial and public-tool events produce semantic Audit and a tested SIEM export subset.

The refresh cookie is `__Host-tg_refresh`, `HttpOnly`, `Secure`, `SameSite=Strict` and `Path=/`, without `Domain`. Auth POST routes require an Origin exactly present in configured HTTPS application origins; missing Origin is rejected. Auth-enabled configuration requires distinct HTTPS application and Auth hostnames. The API routes `/api/auth/*` only on the Auth Host and public API paths only on the application Host. Operational health paths remain available on the API listener. Configurations without Auth issue no Auth cookie and expose no Auth route through the Web gateway.

T4.2 transport hardening rejects duplicate same-name refresh cookies on both refresh and logout before any session mutation. The live PostgreSQL/HTTP test confirms the original session remains valid after those requests. CJSON accepts only exact allowed origins without a path, query or trailing slash; Auth preflight accepts only POST with declared `content-type`/`accept` headers and emits credentialed CORS headers for an allowed Origin. A local two-host Chrome test confirms the refresh cookie is scoped to the Auth hostname. Production DNS, TLS and ingress isolation still need customer deployment evidence.

T4.3-B adds bounded DOCX/ODT ZIP prechecks before LibreOffice and sanitizes user-supplied display filenames in FAQ JSON/SSE metadata. The Web production build emits a nonce CSP for Kit responses, including `frame-ancestors 'none'` and `report-uri /api/security/csp-report`; the API accepts bounded CSP reports through a durable Admission limit and safe Audit event. T4.4 adds a release Web process header layer for adapter-served static assets, with a built-runtime test for static and HTML responses. Browser development mode also inserts a style exception for hot reload; it is not production CSP evidence. Customer TLS/HSTS evidence remains open.

T4.4 adds a generic persisted Authority resolver and canonical application-service facade. The live PostgreSQL matrix covers role and identity grants, root and internal ALL, explicit deny, object and field decisions, ACL, clearance/classification, hierarchy, ownership, absolute and recurring schedules, Jalali days, suspension, termination, and authorization-version invalidation. The facade writes safe semantic decision evidence and a durable SIEM export record before returning a decision; Audit failure prevents protected payload materialization. The live test confirms HUMAN initiating-subject metadata and SIEM retry. T4.4-C inventories every current target production Authority call site in `docs/security/07-t4-authority-decision-boundary.md`, verifies ALLOW and DENY evidence, and adds `ARCH-AUTH-004` to reject production pure-evaluator bypasses. ASVS V16.3.2 is PASS for the current production target; T5 must audit every new consumer. The RAG start gate and the ASVS Level 3 customer-release gate are separate: 173 ASVS controls remain open for release, including 102 to verify during T5.

WebAuthn remains a design blocker. A ceremony initiated by the application page has the application Origin, while refresh credentials and Auth routes use the separate Auth hostname. The RP ID and expected Origin must therefore be configured and verified as one explicit ceremony contract before registration, MFA login and factor management are enabled. Password proof currently issues a session; it does not meet the Level 3 MFA flow. The Auth-enabled target must not be treated as a Level 3 customer release until durable single-use challenges, hardware policy, verified assertions, trusted initial enrollment, recovery, and session effects are implemented and tested.
