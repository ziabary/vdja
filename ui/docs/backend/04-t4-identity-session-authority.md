# T4 identity and session contract (work in progress)

Identity is deployment-global. Membership is keyed by identity and tenant. Authentication verifies a human credential; the Session capability owns tenant-bound sessions and refresh-token families. Authority alone evaluates permissions. Anonymous requests use `actorKind=ANONYMOUS`, null actor/session IDs and the deployment's public tenant.

The production transition proposed for T4 is `credential proof → tenant selection → new tenant-bound session → short-lived access token`. A tenant switch creates a new session context. Access-token claims are identity ID, tenant ID, session ID and authorization version; the database remains canonical. Refresh tokens are high-entropy opaque credentials; only hashes and rotation history are persisted. A refresh consumes the current token atomically. Reuse revokes the family. Revocation and version changes must invalidate already-issued access tokens through a database check on every protected request.

Current T4.1 state: the pure Authority kernel passes 39 conformance cases. PostgreSQL migration `004` owns global identity, tenant membership, password credential, durable login guard, sessions and refresh history. Authentication now resolves credentials and active memberships from PostgreSQL, verifies passwords centrally, and uses durable account/address guards. The optional Auth API provides login with explicit selection for multiple tenants, refresh, logout and a bearer-protected account/session view. Ed25519 access tokens have minimal claims, a five-minute maximum lifetime, issuer/audience and `kid` validation, and keys loaded from secret references. The protected-request verifier checks canonical session, identity, membership, tenant and authorization version in PostgreSQL. The browser proxy forwards Auth Origin/cookie/Set-Cookie only for Auth endpoints. A BrandProfile-based Svelte login page appears only when Auth is enabled, with its access token held in component memory. Unit, transport, PostgreSQL credential/session and loopback HTTP login/refresh/replay/logout tests pass; browser, semantic Audit/SIEM, MFA and authenticated public-service integration remain open. No customer Auth-enabled release is authorized.

The `session_core` schema owns session and refresh history. The `identity` schema owns global identity and tenant membership. `authentication` owns password credentials and login guard facts. `authority` owns permission vocabulary, roles, grants/denies, ACL and clearance facts. Privilege evaluation lives only in `packages/authority/src/index.ts`; it receives explicit time and normalized facts. Access to the new tables through API/Worker application paths is not yet wired, and the new tables must not be treated as a functioning login system.

The password implementation uses Node's standard scrypt with N=2^17, r=8, p=1 and a fresh 128-bit salt; parameter configuration, compromised-password screening and account-recovery policy remain open. Login guards lock account and address keys after bounded failures; the PostgreSQL integration test passed with real credentials and unknown-account lockout. Refresh tokens have 256 random bits and only SHA-256 hashes enter PostgreSQL. Session creation checks active human identity and membership. Refresh rotation locks token/session/membership/identity rows in one PostgreSQL transaction. Reuse of a consumed token revokes the family. Logout revokes the session by hashed refresh credential. Access-token validation rejects revoked or expired sessions, identity or membership suspension, version mismatch and tenant mismatch. Credential-change invalidation, tenant switch, selected/all-session revoke and semantic event export remain open.

The refresh cookie is `__Secure-tg_refresh`, `HttpOnly`, `Secure`, `SameSite=Strict` and `Path=/api/auth`. Auth POST routes require an Origin exactly present in configured allowed origins; missing Origin is rejected. The narrow path conflicts with ASVS V3.3.3's `__Host-` prefix condition, which requires `Path=/`; this remains a documented blocking finding until the policy is resolved. Configurations without Auth issue no Auth cookie and expose no Auth route through the Web proxy.

T4.2 transport hardening rejects duplicate same-name refresh cookies on both refresh and logout before any session mutation. The live PostgreSQL/HTTP test confirms the original session remains valid after those requests. CJSON now accepts only exact allowed origins without a path, query or trailing slash; Auth preflight accepts only POST with the declared `content-type`/`accept` headers and emits explicit credentialed CORS headers for an allowed Origin. These controls do not provide a dedicated Auth host or close V3.3.3 and the full CSRF gate.
