## 2. Conflicts resolved by architecture

1. **Client privileges:** Sepidjoo's `hasPriv`/`hasCRUD` and AIAR role checks cannot be the FAPA UI decision engine. Authority returns capability views; every backend operation still authorizes. No package relocation or helper renaming makes browser interpretation acceptable.
2. **Static versus SSR:** use AIAR's Node adapter baseline, Sepidjoo's generic shell composition and Svelte's request/context isolation. Do not copy a singleton store or AIAR's repository imports. Private data cannot be process-global or serialized into public config.
3. **Totals:** replace Sepidjoo's mandatory-total result shape; a default list must work with only cursor metadata. Random-page UX requires an explicit backend offset contract and separate requested count where needed.
4. **Calendar:** AIAR provides the strongest source; extract once. Sepidjoo picker and FAPA local enhancer become migration bridges and are removed after parity. Business event/holiday policy remains with its owner, supplied as facts/configuration to Calendar Core.
5. **Styling:** retain Bootstrap + SCSS; borrow AIAR component composition/behavior without importing its entire global stylesheet. Scope Sepidjoo overrides and fix direction/breakpoint mistakes.
6. **Sessions:** neither reference alone solves existing FAPA refresh-cookie `Path=/api/` plus authenticated page SSR. Identity must design a separate host-scoped credential or session introspection/bootstrap contract if required; Web cannot widen the refresh cookie to `Path=/` for convenience. [03 §12](03-target-ui-architecture.md#12-authentication-and-tenant-context) specifies the ownership boundary; implementation and security verification precede protected cutover.
7. **AI output:** share operation/Markdown/stream mechanisms. Existing JSON CRM summary stays JSON in the first slice; backend AI Router owns routing and post-commit fallback policy. Partial output cannot become a successful response solely because the connection closed.
8. **Product coupling:** commerce dialogs, AI credits, market events, CRM workflows and Widget publishing stay module-owned. Platform packages and generic shell cannot import module-private logic.
9. **Follow-up:** the selected CRM customer journey does not transfer generic task semantics to CRM. Follow-up is the target owner; a legacy CRM-local task path is only a temporary migration compatibility boundary.

## 3. Decision status

The comparison, shell, API/auth strategy, calendar extraction decision and coexistence model are **approved for U1 foundation implementation**. This approval does not authorize production route cutover, legacy UI removal, Identity cookie changes, CRM or Follow-up production implementation, backend schema changes, ingress switch or production deployment. The [U1 readiness checklist](05-ui-guardrails-and-testing.md#8-definition-of-ready-for-u1) keeps later integration and cutover prerequisites pending.
