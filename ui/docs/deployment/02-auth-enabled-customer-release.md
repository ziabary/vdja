# Auth-enabled customer release gate

Status: **not releaseable**. The T4 migration, cryptographic/session foundation, and current customer C images are development artifacts. API, Web and Worker role images were built and inspected for runtime code, the third-party password-list license and absence of MySQL/MySQL2/Knex packages. The Auth-enabled API image ran anonymous and authenticated Translator, Summarizer, and FAQ requests against PostgreSQL while the local MySQL container was stopped. Web and Worker images have not been tested as a coordinated Auth-enabled release.

T4.1 now includes optional Auth CJSON, external Ed25519 signing key refs with `kid`, database credential verification and rate guards, tenant choice, access-token checks, narrow secure Refresh cookie routes, a branded login page, live Authority on the three public services, tiered Admission, and Human Usage/Audit/SIEM. The API/PG and Chrome suites exercise these paths separately. Password hashing rejects a locally pinned set of 3,000 common policy-valid passwords; no user-facing password change/recovery path exists yet. Before an Auth-enabled customer release, complete and verify: one-shot first-user bootstrap without default password; hardware-backed MFA; password change/recovery and screening on operational paths; session listing/revocation; full Authority persistence semantics including ACL/classification/clearance/recurring grants; full browser account/session and CSRF attack coverage; all 345 ASVS 5.0.0 Level 3 control assessments; and coordinated customer Web/Worker runtime validation. Resolve ASVS V3.3.3 using the decision in `docs/security/03-t4-refresh-cookie-decision-fa.md`. Normal API/Worker/Web images need SBOM and dependency checks after the final changes.

Migration-only MySQL access stays in the explicit development CLI `migrate:public-tools:mysql-to-pg`; it is absent from the normal customer runtime lock and the customer C `1.0.1` images.
