# T5-R3 — Legacy RAG UX Parity and Functional Bring-Up
#
# PRIMARY OBJECTIVE:
# Restore the legacy Targoman RAG user experience on top of the NEW
# Document / File Management / Knowledge / Authority / AI Router architecture.
#
# THIS IS A FUNCTIONAL MIGRATION TASK.
#
# Do NOT start another security-hardening project.
# Do NOT rerun the full ASVS program merely because files changed.
# Do NOT weaken or bypass existing Authority/File Management/AI Router boundaries.
#
# Highest priority:
#
#   GET THE RAG PAGE WORKING FOR A HUMAN USER.
#
# The result must feel like the OLD RAG product, not like an internal
# Knowledge administration/debug screen.

====================================================================
0. DO NOT DESIGN FROM THE CURRENT /knowledge PAGE
====================================================================

The current `/knowledge` UI is NOT the desired product UX.

It exposes implementation concepts such as:

Knowledge Space
classification
Document creation
manual membership
manual index/rebuild concepts

directly to the ordinary user.

That is useful as an engineering/debug interface but it is not the legacy
RAG user experience.

The target user experience must be derived from the LEGACY RAG source.

5. HIDE KNOWLEDGE-SPACE COMPLEXITY
====================================================================

An ordinary RAG user must not need to understand Knowledge Spaces.

For the old "اسناد شما" experience, automatically resolve an appropriate
personal RAG Knowledge Space for the current:

has the required permission.

Do NOT create it by direct SQL from the UI.

Give it a stable semantic identity such as:

PERSONAL_RAG

or the repository-consistent equivalent.

Do not expose its UUID to the user.

====================================================================
6. PERSONAL SPACE SEMANTICS
====================================================================

The default RAG experience should work like the legacy product:

"my documents"
→ documents in the user's default RAG knowledge context.

Uploading a document should automatically:

→ commit Asset/Version
→ process
→ attach to the personal RAG Space
→ schedule indexing
→ become available to RAG

The user should NOT have to manually:

create a Document record
select a Knowledge Space
add membership
request rebuild

for ordinary use.

Those are implementation details.
