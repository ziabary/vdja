9. LEGACY KEY LOGIN — REQUIRED COMPATIBILITY
====================================================================

Implement a target-native LEGACY_KEY authentication method compatible with
existing legacy keys.

Important security correction:

DO NOT reproduce the old browser-side:

raw key
→ MD5 in browser
→ send MD5 as credential

because the MD5 value becomes a reusable password-equivalent.

Instead:

browser sends the RAW legacy key only over the protected Auth TLS channel;

server computes the legacy compatibility digest internally;

server compares it to the migrated legacy credential verifier.

The legacy digest exists ONLY for compatibility with previously issued keys.

Do not use MD5 for any new cryptographic purpose.

====================================================================
10. LEGACY KEY CREDENTIAL STORAGE
====================================================================

Legacy key material belongs to Authentication credential persistence.

It is NOT:

Identity ID
tenant ID
authorization grant
session ID
resource key

Represent it explicitly as a legacy compatibility credential associated with
one canonical target Identity.

Never copy legacy usrKey into access-token claims.

Never allow business modules to inspect it.

Do not write raw key or legacy digest into Audit/SIEM/logs.

====================================================================
11. LEGACY KEY MIGRATION / DEVELOPMENT SEED
====================================================================

====================================================================
12. LEGACY SELF-PROVISIONING
====================================================================

The old system automatically created an account for an unknown key.

Do NOT silently preserve that behavior globally.

Support it only through an explicit typed policy such as:

legacyKey.selfProvision

Default:

false

For the DEVELOPMENT profile only, it may be enabled explicitly to reproduce
the old quick-start workflow.

If enabled:

- require one explicitly configured onboarding tenant;
- create a minimal Identity and membership;
- assign only the explicit onboarding Authority template;
- do not infer privileges from the key;
- audit the provisioning event without recording the key;
- apply durable abuse/rate limits.

CUSTOMER_L3 must not silently enable legacy-key self-provisioning.
