# T4 — Security Level 3, Identity, Authentication, Session,
# Authority, Authenticated Accounting and Public-Service Policy

T3 is COMPLETE and is the baseline for this task.

T3 already provides:

- PostgreSQL-only anonymous Translator/Summarizer/FAQ;
- CJSON Configuration;
- AI Router;
- semantic Audit;
- database mutation Audit;
- Usage Accounting;
- Admission Control;
- Observability;
- SIEM push;
- customer-specific release images;
- runtime branding;
- successful MySQL-off execution.

T4 introduces authenticated operation without breaking anonymous operation.

This task also closes the four T3 verification issues identified during review,
performs an OWASP ASVS 5.0 Level 3 security verification, implements Identity /
Authentication / Session / Authority, and extends the three existing public
services with identity-aware authorization/accounting/limits.

T4 does NOT implement RAG.

RAG begins only after all T4 gates pass.

====================================================================

Do not build one generic "Auth" god-module.

Maintain separate canonical responsibilities:

Authentication
    → proves identity

Session
    → owns authenticated session lifecycle

Authority
    → sole canonical authorization decision engine

Usage
    → records what was consumed

Admission Control
    → decides whether new work may begin

Audit
    → records accountable actions

Business modules
    → declare resources, operations and facts
    → never evaluate authorization themselves

    ↓

    ↓
Global Identity
    ↓
Tenant Selection
    ↓
Tenant-Bound Session
    ↓

    ↓
Execution Context
    ↓
Authority
    ↓
Admission Control
    ↓
Application Service
    ↓
AI Router / File Processing / Persistence
    ↓
Usage + Audit + Observability

Anonymous flow remains valid:

ANONYMOUS Execution Context
    ↓
Anonymous Admission Policy
    ↓
same module services

No public module should need separate authenticated and anonymous
implementations.

3.3 SIEM UNKNOWN / Timeout Semantics
--------------------------------------------------------------------

A timeout does not prove delivery failure.

Simulate:

receiver accepts event
but response is lost / connection closes before acknowledgment

Expected:

status = UNKNOWN / UNRESOLVED

Automatic retry is permitted only when:

- target protocol supports idempotency; or
- destination is explicitly configured as duplicate-tolerant.

A stable event ID alone does not prove the remote destination honors
idempotency.

Test:

- true idempotent receiver;
- duplicate-tolerant receiver;
- receiver with no idempotency guarantee;
- 503 before acceptance;
- timeout after possible acceptance;
- permanent 4xx;
- Worker restart.

Do not blindly retry unresolved external side effects.

====================================================================
11. PASSWORD STORAGE
====================================================================

Use a modern password hashing mechanism consistent with ASVS 5 Level 3 and
current OWASP password-storage guidance.

Parameters must have deployment-configurable defaults with platform minimum
security bounds.

Never store plaintext or reversible passwords.

Never log password material.

Do not silently migrate weak legacy password hashes into trusted modern state.

If legacy password migration is needed:

- inspect the actual legacy algorithm;
- document it;
- either perform a safe verified upgrade-on-login;
- or require password reset;
- never pretend an unknown/insecure hash is equivalent.

16. ACCESS TOKEN
====================================================================

- signed;
- tenant-bound;
- session-bound;

18. REFRESH TOKEN
====================================================================

Refresh token is a session credential.

Use:

HttpOnly
Secure
appropriate SameSite policy
narrow Path

Do NOT widen the refresh cookie to `/` merely to make SSR easier.

Raw refresh tokens are never stored server-side.

Store only an approved cryptographic representation/hash.

====================================================================
19. REFRESH ROTATION
====================================================================

Refresh tokens rotate on use.

Maintain refresh-token family state.

Expected:

refresh token A
→ use
→ invalidate A
→ issue B

Reuse of A after rotation:

→ detect replay
→ revoke affected family/session according to policy
→ invalidate access path
→ produce high-priority semantic/security audit
→ SIEM eligible event

Test concurrent refresh races.

21. LOGOUT / REVOCATION

22. AUTHORIZATION VERSION
====================================================================

Authority-affecting changes increment/invalidate authorization version.

- role changed;
- explicit grant changed;
- explicit deny changed;
- tenant membership suspended;
- ACL changed where session digest depends on it;
- break-glass state changed.

Stale session/token state must fail safely.
