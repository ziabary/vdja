# Task U1.2 — Persian Foundation Showcase, Localization Baseline & One-Command Development

U1/U1.1 established the target SvelteKit foundation, but the current UI is not yet practically reviewable by a human.

The foundation pages are mostly English and do not expose enough implemented primitives to visually evaluate:

```text
IRANSansX
FontAwesome
RTL/LTR
fa-num
forms
Jalali calendar
tables
Markdown
overlays
feedback
loading
AI operation states
```

Development startup is also unnecessarily verbose.

This task makes the foundation **human-reviewable and developer-friendly** before any CRM or business vertical slice begins.

Do not migrate CRM, Widget, Follow-up, Secretariat or any other business screen.

Do not switch production ingress.

Do not modify backend database or Identity semantics.

# 3. Objectives

U1.2 has exactly three primary objectives:

```text
1. Make Persian the useful default development presentation.
2. Build one comprehensive development-only Component Showcase.
3. Make normal development start with `npm run dev`.
```

A small localization foundation may be introduced because hard-coded English shell text must not become the target pattern.

---

# 4. Persian Is the Default UI Locale

The target product must support multiple languages, but the default development/demo experience for this deployment is Persian.

The shell should no longer display generic English literals such as:

```text
Skip to content
Home
Theme
Guest
Support
Legal
Dashboard
Administration
Choose date
Close
Previous month
Next month
```

directly from components.

Do not merely replace English literals with hard-coded Persian literals throughout the component tree.

Introduce one minimal canonical localization boundary.

---

# 5. Minimal Localization Foundation

Implement a small typed localization mechanism appropriate for the current foundation.

Do **not** introduce a large internationalization framework unless repository/reference evidence proves it necessary.

Preferred conceptual ownership:

```text
apps/web/src/lib/i18n/
```

or another precise UI-owned location.

It must support at minimum:

```text
fa
en
```

with:

```text
default locale = fa
default direction for fa = rtl
default direction for en = ltr
```

Messages must be statically typed or otherwise checked so missing keys are discoverable.

Do not use arbitrary string lookups scattered through the application.

---

# 6. Localization Ownership

Localization owns presentation text only.

It must not own:

- business semantics;
- authorization decisions;
- backend error meaning;
- tenant policy;
- dates/calendar calculations;
- BrandProfile values.

Brand names still come from `BrandProfile`.

Calendar arithmetic still belongs to Calendar Core.

---

# 7. Locale Context

Provide one canonical locale context to the shell and shared presentation components.

It should expose something equivalent to:

```text
locale
dir
messages / translator
number presentation helpers if truly presentation-only
```

Do not create separate locale stores per module.

---

# 8. SSR Safety

Locale selection and rendering must be SSR-safe.

Requirements:

- SSR and hydration agree on locale and direction;
- no initial English flash before Persian hydration;
- `<html lang="fa" dir="rtl">` for Persian;
- locale must not depend on top-level browser globals;
- locale-sensitive shell text must render correctly during SSR.

# 41. Proxy Constraints

If a Vite API proxy is added:

- target is development-only;
