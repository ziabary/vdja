# Task U0 — UI Architecture, Reference Reconciliation & Migration Contract

We are preparing the largest UI migration in the FAPA / Targoman AI Platform:

```text
current legacy frontend
    →
SvelteKit 5 target frontend
```

This task is **U0 only**.

Do not implement the new SvelteKit application yet.

Do not migrate production UI.

Do not delete legacy UI.

Do not change backend behavior.

The objective is to produce a precise, evidence-based UI migration contract before implementation begins.

The target must be derived from:

1. the current FAPA/legacy UI implementation;
2. the actual Sepidjoo frontend implementation;
3. the actual AIAR frontend/shared UI implementation;
4. the approved FAPA architecture documents and AGENTS rules.

Do not redesign from memory when working implementations already exist.

---

# 1. Governing Principle

The core rule for U0 is:

```text
Inspect implementations first.
Reconcile second.
Design target third.
Implement later.
```

Sepidjoo and AIAR are **reference implementations**, not unquestionable specifications.

If they differ:

- identify the difference;
- explain why;
- determine which behavior is compatible with FAPA architecture;
- preserve the strongest reusable implementation where appropriate;
- do not merge conflicting semantics silently.

# 70. Reuse over Copying

When Sepidjoo or AIAR contains a high-quality reusable component/package:

Prefer:

```text
reuse
extract shared package
workspace dependency
submodule/reference
upstream fix
```

over copy/paste forks.

Do not copy a working shared component into FAPA and let implementations diverge unless an explicit architecture reason requires it.

---

# 71. Preserve Canonical Ownership

Examples:

```text
Calendar logic
→ calendar-core

Calendar UI
→ calendar-svelte

Generic visual primitives
→ ui-core

Brand runtime config
→ branding

Auth decision
→ backend Authority

AI routing
→ AI Router

Business page
→ owning module/app contribution
```

Frontend convenience must not create a second semantic owner.

---

# 72. No Authorization Logic in UI

The UI may receive capability/presentation information.

It must not become the authority.

Do not design:

```ts
if (role === 'manager')
if (privs.ALL)
if (ownerId === currentUserId)
```

as security enforcement.

UI visibility is UX.

Backend Authority decides access.

---

Use Sepidjoo to preserve proven SvelteKit/platform UX patterns.
