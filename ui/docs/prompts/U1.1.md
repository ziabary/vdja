U1 foundation is implemented and structurally accepted, but several foundational compatibility and white-label requirements were missed.

This task corrects those issues **before any business vertical slice begins**.

Do not change production ingress.

Do not remove legacy UI.

Do not change backend Identity/database semantics.

## Target frontend toolchain modernization (added to U1.1)

Modernize `apps/web` and the five new UI packages before accepting this correction. The target tuple is Node 22 LTS (at least 22.17), Svelte 5.57.1 or newer, SvelteKit 3, adapter-node 6, vite-plugin-svelte 7, Vite 8.0.12 or newer, Vitest 5, and the latest stable TypeScript 6. Use exact compatible versions and verify them against the upstream migration guides and npm peer/engine metadata. Do not use TypeScript 7 for Svelte tooling yet.

Migrate SvelteKit configuration from `svelte.config.js` into `vite.config.ts`, replace removed `$lib` and `$app/paths` usage, and verify strict checking, component tests, Node SSR, fonts, SCSS, and route smoke tests under Node 22. Preserve Node 20 compatibility for the legacy Express application during coexistence; do not upgrade legacy/backend dependencies as part of U1.1. Record the pinned tuple and any runtime limitation in the U1.1 Activity Report and implementation documentation.

# 3. Critical Product Identity Rule

The platform codebase is a Targoman platform.

**FAPA is a deployment/customer brand, not the code/package namespace.**

Canonical distinction:

```text
Internal product/package namespace
    → Targoman

Deployment visual identity
    → BrandProfile

FAPA name/logo
    → only when the active deployment BrandProfile is FAPA
```

Therefore:

```text
@fapa/*
```

is forbidden as an internal package scope.

The canonical internal package scope is:

```text
@targoman/*
```

# 5. Do Not Turn `Targoman` Into a Hard-Coded UI Brand

Changing package namespace to `@targoman/*` does **not** authorize:

```text
Targoman
```

as a hard-coded visual brand.

The Web UI must render:

```text
display name
logo
favicon
support identity
legal/footer identity
visual brand tokens
```

from the active `BrandProfile`.

Examples:

```text
FAPA deployment
→ FAPA name/logo

another customer deployment
→ that customer's name/logo
```

The internal package namespace must never determine the displayed brand.

# 11. Preserve the Existing `fa-num` Contract

The legacy project has an important shared class:

```css
.fa-num
```

Its purpose is Persian/Eastern-Arabic numeral presentation where the UI requires Persian number glyphs.

Inspect the exact legacy implementation and preserve its intended behavior.

Do not guess the existing font-feature/font-family implementation.

Target rule:

```text
canonical numeric value
    ≠
presentation glyph
```

`fa-num` affects presentation.

It must not corrupt:

- API numeric values;
- IDs;
- machine-readable values;
- canonical form serialization.

Use `fa-num` on UI elements where Persian number presentation is required.

This is especially important for:

- numeric labels;
- counts;
- Persian-facing dates;
- amounts when Persian display is intended;
- table cells;
- dashboard statistics.

Do not apply it blindly to:

- email;
- URLs;
- code;
- tokens;
- English model names;
- identifiers requiring Latin digits.
