# ارزیابی مهندسی OWASP ASVS 5.0.0 سطح ۳

**وضعیت: ناقص / PARTIAL.** این متن ادعای گواهی ASVS یا تکمیل T4 نیست. `READY_FOR_RAG_SECURITY_GATE = NO`.

منبع رسمی: [فایل تخت ASVS 5.0.0](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/docs_en/OWASP_Application_Security_Verification_Standard_5.0.0_en.flat.json)، SHA-256: `8201b20eec2908c3380ac600c91c8ba746346fbb808859366abb232027532311`.

شاهد ماشینی: `reports/security/asvs-5.0-l3.json`. هر ۳۴۵ الزام سطح ۱، ۲ و ۳ با شناسهٔ نسخه‌دار و متن اصلی ثبت شده است. پس از T4.1، چهار الزام کوکی با شاهد اختصاصی `PASS`، شش نقص قطعی `FAIL` و ۳۳۵ الزام `NOT_VERIFIED` هستند. سیاست دامنه محافظه‌کارانه است: تا زمانی که دلیل فنی اختصاصی برای N/A ثبت نشده، الزام قابل اعمال شمرده می‌شود. شرح فارسی برای ده کنترل بررسی‌شده ثبت شده است و برای باقی کنترل‌ها تا بازبینی اختصاصی تهی می‌ماند.

## خلاصهٔ مدیریتی و دامنه

ارزیابی شامل Web/SvelteKit، API، Worker، PostgreSQL، پیکربندی CJSON و secrets، تصاویر مشتری، AI Router، SIEM، فایل/streaming، هویت، احراز هویت، نشست، توکن، Authority، مستأجر، Usage/Admission/Audit و زنجیرهٔ تأمین است. این یک بررسی مهندسی داخلی است؛ آزمون نفوذ دستی یا تأیید بیرونی انجام نشده است. شش نقص قطعی و ۳۳۹ الزام راستی‌آزمایی‌نشده مانع انتشار Auth و شروع RAG است.

## روش، ماتریس و شدت

روش این مرحله شامل خواندن معماری و کد، آزمون واحد، PostgreSQL و HTTP زنده، مرورگر Chrome، گیرندهٔ HTTP شبیه‌سازی‌شده، تصویر تازهٔ customer-c با MySQL خاموش و بررسی وابستگی runtime بود. ماتریس کامل الزام‌ها، نتیجهٔ `PRE-T4` و `POST-T4`، دامنه، روش مورد نیاز، خطر و اصلاح در JSON همراه آمده است. دسته‌های احراز هویت، نشست، مجوزدهی، توکن، ارتباط امن، حفاظت داده و ثبت امنیتی تا آزمون اختصاصی **شدت مسدودکننده** دارند. شمار فعلی مسدودکننده‌ها ۳۴۱ است؛ هیچ موردی با حدس به N/A یا PASS منتقل نشده است. گذر آزمون‌های عملکردی زیر به‌تنهایی اثبات همهٔ اجزای یک الزام ASVS نیست.

## یافته‌های قطعی پیش از T4

- `/ready` نبود endpoint سالم را به‌اشتباه `DEGRADED` برمی‌گرداند؛ در اصلاح چهارم T3 رفع شد.
- تصویر مشتری `mysql2` داشت؛ قفل runtime اصلاح و تصویر تازهٔ API مشتری C ساخته و بدون MySQL اجرا شد. پوشش تصویر Web/Worker و انتشار Auth هنوز باز است.
- SIEM وضعیت نامعلوم را قابل retry می‌کرد؛ سیاست پیش‌فرض اکنون UNKNOWN را نگه می‌دارد، ولی آزمون گیرنده/Restart زنده باز است.
- مسیر target در T4 پیشین ورود و توکن دسترسی نداشت؛ در T4.1 مسیر اختیاری ورود، توکن و Authority در سه ابزار عمومی اضافه شد. MFA هنوز وجود ندارد.

## شواهد پس از تغییر و کنترل‌های جبرانی

- kernel Authority همان کد تولیدی است که ۳۹ آزمون conformance را می‌گذراند. API برای درخواست‌های HUMAN سه ابزار عمومی Session را بررسی، Authority را فراخوانی و سپس Admission را اجرا می‌کند. آزمون PostgreSQL/HTTP مستأجر A/B/AB، grant غیرتجمیعی، deny، `ALL` و RLS گذشت؛ اتصال کامل ACL، classification، clearance و برنامهٔ تکراری grant هنوز باز است.
- جدول نشست و تاریخچهٔ refresh در PostgreSQL و آزمون زندهٔ چرخش، بازپخش و مسابقهٔ هم‌زمان وجود دارد. امضای Ed25519، `kid`، رد الگوریتم/issuer/audience نادرست، اعتبار زمانی و بار حداقلی توکن آزمون واحد دارند. اعتبارسنجی نشست از PostgreSQL در درخواست محافظت‌شده زنده آزموده شد. عمرهای نشست از CJSON معتبر با سقف تغییرناپذیر خوانده می‌شوند؛ مقایسهٔ عمرهای پایدار و guard ورود از زمان PostgreSQL استفاده می‌کند.
- کوکی `__Secure-tg_refresh` دارای `HttpOnly`، `Secure`، `SameSite=Strict` و `Path=/api/auth` است. کوکی‌های غیرحساس locale/theme با `__Host-`، `Secure` و `Path=/` نوشته می‌شوند. مسیرهای refresh و logout Origin را الزام می‌کنند و Web proxy فقط برای مسیر Auth آن را همراه کوکی منتقل می‌کند. آزمون HTTP زندهٔ ورود، چرخش، بازپخش، مسابقهٔ refresh، خروج و پیکربندی Auth-disabled و آزمون Chrome گذشت. چهار کنترل V3.3.1، V3.3.2، V3.3.4 و V3.3.5 با شاهد مختص خود PASS شدند؛ انتخاب معماری Refresh در `03-t4-refresh-cookie-decision-fa.md` ثبت شده و V3.3.3 همچنان FAIL است.
- صفحهٔ ورود Svelte از BrandProfile استفاده می‌کند و فقط در پیکربندی Auth-enabled نمایش داده می‌شود؛ آزمون Chrome نگهداری توکن فقط در حافظه، انتخاب مستأجر، خروج و درخواست‌های احراز‌شدهٔ سه ابزار را بررسی کرد. backend مرورگر در این آزمون mock است؛ آزمون مستقل PostgreSQL/HTTP backend واقعی را پوشش می‌دهد. رفتار چندتب هنوز بررسی نشده است.
- سه ابزار برای HUMAN حد ورودی، آپلود، خروجی/توکن و نرخ/هم‌زمانی متفاوت از ANONYMOUS دارند. Authority ردهٔ limit را می‌دهد، Configuration مقدار را نگه می‌دارد و Admission تصمیم نهایی را می‌گیرد. Usage و Audit با actor/session/tenant و تحویل SIEM در آزمون زنده بررسی شدند.
- هش گذرواژه با scrypt و نمک تصادفی آزمون شده است؛ guard پایدار برای حساب و آدرس در PostgreSQL با هویت واقعی و قفل حساب ناشناس در آزمون integration زنده گذشت. تابع ایجاد هش اکنون ۳۰۰۰ گذرواژهٔ رایجِ سازگار با سیاست طول ۱۵ تا ۱۲۸ را رد می‌کند. مجموعه از فهرست رتبه‌بندی‌شدهٔ SecLists xato-net top 1M مشتق شده است (SHA-256 منبع: `424a3e03a17df0a2bc2b3ca749d81b04e79d59cb7aeec8876a5a3f308d0caf51`؛ آخرین رتبهٔ انتخاب‌شده ۷۹۰۰۳۹). فقط digestها در bundle هستند و مجوز MIT همراه تصویر قرار می‌گیرد. مسیر ثبت/تغییر گذرواژه، بازیابی و MFA هنوز باز است؛ V6.2.4 تا آزمون مسیر عملیاتی PASS نمی‌شود.
- تصویر تازهٔ API مشتری C از کد فعلی ساخته شد؛ runtime فاقد MySQL/MySQL2/Knex بود و در حالی که container MySQL خاموش بود، درخواست ناشناس و احراز‌شدهٔ Translator، Summarizer و FAQ را با PostgreSQL و provider آزمایشی پاسخ داد. تصویر Web/Worker و SBOM/اسکن همین build هنوز بررسی نشده‌اند؛ خروجی نصب build وابستگی‌های دارای هشدار را نشان داد.
- کنترل جبرانی عملی: هیچ مسیر login یا cookie در تصویر منتشرشدهٔ T3 فعال نشده است؛ ابزارهای عمومی همچنان در حالت ناشناس T3 کار می‌کنند.

## موارد N/A و تأییدنشده

فعلاً N/A = ۰، PASS = ۴، FAIL = ۶ و NOT_VERIFIED = ۳۳۵. یافته‌های قطعی: `V3.3.3` پیشوند کوکی Refresh، `V6.2.2` تغییر گذرواژه، `V6.2.4` غربال در مسیر عملیاتی تغییر/ثبت گذرواژه، `V6.3.3` عامل سخت‌افزاری مقاوم در برابر فیشینگ، `V6.3.5` اعلان تلاش مشکوک و `V6.4.3` بازیابی امن. کوکی Refresh محدود به مسیر در برابر جعل میان‌میزبانی، همراه با Origin اجباری و SameSite، کنترل جبرانی نسبی است ولی الزام `__Host-` را برآورده نمی‌کند. الزام‌های شرطی مانند WebRTC و OAuth پس از بازبینی فنی مستقل ممکن است N/A شوند؛ صرف نبود پیاده‌سازی برای این تصمیم کافی نیست. شرح فارسی کنترل به کنترل نیز ناقص است. ریسک باقیمانده برای انتشار Auth بالا و غیرقابل‌قبول است.

## معیار بستن ارزیابی

برای هر الزام باید شرح فارسی دقیق، دامنهٔ واقعی، روش راستی‌آزمایی، شاهد خودکار/دستی، مسیر کد/آزمون، نتیجه، خطر و اصلاح ثبت شود. سپس آزمون‌های Web، SSR، API، Worker، PostgreSQL، secrets، CJSON، تصاویر، AI Router، SIEM، آپلود، streaming، HTTP headers، CSP/CORS/CSRF، injection، session/tenant و supply chain انجام و نتیجهٔ پس از T4 جدا از مبنای پیشین ثبت شود. `NOT_APPLICABLE` فقط با دلیل فنی مختص همان شناسه مجاز است. تا بستن موارد قابل اعمال، دروازهٔ RAG بسته می‌ماند.
